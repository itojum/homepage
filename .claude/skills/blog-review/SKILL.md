# ブログ記事レビュー

このリポジトリ（Astro 製の個人サイト）のブログ記事をレビューするための基準。
記事は `src/content/blogs/<slug>/index.md`（画像なしなら `src/content/blogs/<slug>.md`）に置かれる。
frontmatter のスキーマは `src/content.config.ts`、書き方は `README.md` の「ブログ記事の書き方」を参照する。

## レビューの姿勢

- 目的は「執筆者が気持ちよく直せること」。添削ではなく伴走として、良い点も具体的に伝える
- 執筆者の文体（「こんにちは！いとじゅんです！」のような口語・感嘆符を含むカジュアルな文体）は個性として尊重する。文体そのものの書き換えは求めない
- 下書き（GitHub の Draft PR）の段階では本文が未完成でもよい。未完成部分の指摘は「公開前に」と添えて軽めにする
- 指摘には必ず理由と修正案を添える。修正案は ```suggestion ブロックで示せるときは示す
- 1 つの記事で同じ種類の指摘を何度も繰り返さない。代表例を 1〜2 か所挙げ、「ほかにも同様の箇所があります」とまとめる
- 確信がない技術的な指摘は断定せず、「〜ではないでしょうか」「確認をおすすめします」と書く

### 重要度ラベル

指摘の先頭に次のラベルを付ける。

| ラベル | 意味 |
| --- | --- |
| `[must]` | 公開前に直すべきもの（誤り、ビルドエラー、誤字、リンク切れ、frontmatter の不備など） |
| `[should]` | 直すと明確に読みやすくなるもの |
| `[nits]` | 細かい表記・好みの範囲 |
| `[good]` | 良い点 |

## チェック項目

### 1. frontmatter

- `title`: 記事の内容が一目でわかるか。検索結果や SNS で切れにくい長さ（目安 30〜40 文字程度）か。何について・誰向けか・何が得られるかが伝わるか
- `description`: 空になっていないか（公開時は `[must]`）。一覧や OGP に表示されるため 80〜120 文字程度で、記事の要点と読者が得られることを書く。本文冒頭のコピペや「〜について書きました」だけで終わっていないか
- `publishedAt`: 公開予定日として妥当か。内容を更新した場合は `updatedAt` を付けるとよい
- `eyecatch`: 未設定なら設定を提案する（`[should]`）。相対パス（`./eyecatch.png`）の場合はファイルが同じフォルダに存在するか
- `category`: 既存記事のカテゴリ（例：「技術」「イベント」）と表記がそろっているか
- `tags`: 空でないか。既存記事のタグと表記揺れがないか（例：`Javascript` / `JavaScript`、`参加レポ` / `参加レポート`）。必要なら `src/content/blogs` を Grep して既存タグを確認する

### 2. 構成

- 冒頭で「何の記事か」「誰向けか」「読むと何がわかるか」が伝わるか
- 見出しは `##` から始まっているか（`#` はタイトルとして使われる）。`##` → `####` のようにレベルを飛ばしていないか
- 見出しだけを読んで流れがわかるか。1 つのセクションが長すぎないか
- 結論・まとめがあるか。技術記事なら前提条件（環境、バージョン）が書かれているか
- 参考にした資料や公式ドキュメントへのリンクがあるか

### 3. 読みやすさ・文章

- 一文が長すぎないか（目安 80〜100 文字以上は分割を検討）。読点が多すぎないか（1 文に 4 つ以上）
- 主語と述語の対応がねじれていないか。修飾語がどこに係るか曖昧でないか
- 同じ助詞の連続（「〜の〜の〜の」「〜が〜が」）、二重否定、冗長な表現（「〜することができる」→「〜できる」、「〜という形になる」など）
- 「です・ます」と「だ・である」が意図せず混在していないか
- ら抜き言葉、い抜き言葉
- 指示語（「これ」「それ」「この方法」）が何を指すか明確か
- 箇条書き・表・図にしたほうが伝わる箇所がないか

### 4. 表記揺れ・表記ルール

- 同じ語の表記がそろっているか（例：「サーバー」/「サーバ」、「ユーザー」/「ユーザ」、「行う」/「行なう」、「出来る」/「できる」、「〜の時」/「〜のとき」）
- 製品名・技術名の正式表記（例：`GitHub`、`JavaScript`、`TypeScript`、`Node.js`、`Cloudflare Workers`、`Astro`、`Ruby on Rails`）
- 全角・半角の混在（英数字は半角、全角英数字を使っていないか）。半角と全角の間のスペースの有無が記事内でそろっているか
- 漢字とひらがなの使い分け（補助動詞・形式名詞はひらがなが読みやすい：「〜して頂く」→「〜していただく」、「〜する事」→「〜すること」）

### 5. 誤字脱字

- 誤変換、タイプミス、送り仮名の誤り、助詞の抜け・重複（「をを」「にに」）
- 固有名詞（人名、イベント名、書籍名、サービス名）の誤記
- 日付・数値・バージョン番号の不整合（本文と frontmatter、本文内の前後）

### 6. 技術的な正確さ

- 説明やコードに誤り、古い情報、非推奨の API がないか
- コードが説明どおりに動くか（変数名の不一致、import 漏れ、構文エラーなど）
- バージョンに依存する内容ならバージョンが明記されているか
- セキュリティ上の問題（API キーやトークン、個人情報、社外秘情報の写り込み）がないか。見つけたら `[must]`
- 断定しすぎていないか。推測や個人の感想は事実と区別して書かれているか

### 7. コードブロック

- 言語指定があるか（```` ```ts ```` など）。シェルは `bash` / `sh`、出力は `text` など
- ファイル名を示すと読みやすい場合は `title="hello.ts"` の付与を提案する（例：```` ```ts title="hello.ts" ````）
- インラインコード（`` ` ``）にすべきコマンド名・ファイル名・関数名が地の文のままになっていないか
- コードが長すぎる場合は要点だけに絞るか、省略を明示しているか

### 8. 画像・リンク・埋め込み

- 画像に内容がわかる alt テキストがあるか（`![](./a.png)` や `![image](./a.png)` は `[should]`）。スクリーンショットなら何の画面かを書く
- 画像は記事と同じフォルダに置き、相対パス（`./xxx.png`）で参照しているか。参照先のファイルが存在するか（Glob で確認する）
- 同じフォルダに変換後に同名になる画像（`foo.png` と `foo.jpg`）がないか（WebP 変換で衝突する）
- 画像に個人情報や秘匿情報が写り込んでいないか、ファイル名から推測できる範囲で注意を促す
- リンクテキストが「こちら」だけになっていないか
- 埋め込み（X のポスト、YouTube、Speaker Deck、GitHub など）にしたい URL は前後を空行で挟んで 1 行で書く必要がある。意図せずリンクカード化・非カード化していないか

### 9. 読者への配慮

- 想定読者に対して前提知識の説明が過不足ないか。専門用語・略語は初出で説明やリンクがあるか
- 手順記事なら、読者が再現できるだけの情報（環境、コマンド、期待する結果）があるか
- 特定の人や団体を不用意に傷つける表現、差別的な表現がないか
- イベントレポートなどで他者の名前や写真を出す場合、配慮が必要そうなら一言添える

## 出力のしかた

1. 変更された行に対する具体的な指摘は、その行へのインラインコメントとして残す
   - 1 コメント 1 指摘。先頭に重要度ラベルを付ける
   - 修正案は可能なら ```suggestion ブロックで示す（suggestion は対象行を丸ごと置き換える内容にする）
   - 差分に含まれない行にはインラインコメントを付けられないので、サマリーに回す
2. 最後にサマリーコメントを 1 件だけ投稿する。形式は次のとおり

```markdown
## 📝 ブログレビュー

対象: `src/content/blogs/<slug>/index.md`

### 総評
（2〜3 文。記事の良い点と、全体として一番効く改善点）

### frontmatter
- [x] title
- [ ] description（未記入）
- [ ] eyecatch
- [x] tags

### 主な指摘
- [must] …
- [should] …
- [nits] …

### 良かった点
- …
```

- 指摘がない項目は書かなくてよい。全体で長くなりすぎないようにする
- 複数の記事が対象の場合は、記事ごとに見出しを分ける
